# Slidestyle HTML

발표는 문서가 아니다. 읽는 사람이 스스로 속도를 정하는 문서와 달리, 발표는 **말하는 사람이 한 화면씩 열어 보이는 매체**다. 이 덱은 충분한 텍스트와 설명을 담되, 제목·문단·강조의 위계와 순차 등장으로 청중이 내용을 따라갈 수 있게 만든다.

이 스킬은 그 매체에 맞는 단일 HTML 덱을 만든다. 의존성 없이 브라우저에서 바로 열리고, 프로젝터에서 안 깨지고, 발표 중 사고가 나지 않는 것까지가 범위다.

## 이 덱의 형태

- **단일 `.html` 파일.** 빌드 도구 없음, npm 없음. 파일 하나를 더블클릭하면 열린다.
- **1920×1080 논리 무대**를 `transform: scale()`로 화면에 맞춘다. 창 크기가 바뀌어도 레이아웃이 재계산되지 않으므로, 발표 중에 글자가 재배치되는 사고가 없다.
- **휠·키보드**로 즉시 넘긴다. 마우스 우클릭 또는 `F`로 전체화면을 전환한다. 해시 딥링크(`#/7`)로 특정 장을 바로 연다.
- **자동 순차 등장:** 장에 진입하면 제목·본문·도표가 짧은 간격으로 부드럽게 이어서 나타난다. 한 장 안의 요소를 보기 위해 여러 번 누르게 하지 않는다.
- 필요하면 **라이브 위젯**(계산기, 슬라이더)과 **QR**을 넣는다. 외부 라이브러리 없이 직접 짠다.

## 기본 조작과 화면 처리

이 규칙은 새 덱과 기존 덱 수정 모두에 적용하며, 골격·참고 문서의 기본값과 충돌하면 이 규칙을 우선한다.

- **필수 조작:** 휠 아래/위로 다음/이전 장을 이동한다. 다음 장은 `→`, `↓`, `PageDown`, `Space`, `Enter`, 이전 장은 `←`, `↑`, `PageUp`, `Shift+Space`, `Backspace`를 지원한다. 덱 탐색으로 처리한 키는 브라우저 스크롤 등 기본 동작을 막는다. `Home`은 첫 장의 초기 상태, `End`는 마지막 장의 모든 단계가 보이는 상태로 즉시 이동한다. 첫 장과 마지막 장에서는 범위를 벗어나거나 순환하지 않는다.
- **한 번의 입력으로 한 장 이동:** 다음/이전 조작은 각각 다음/이전 슬라이드로 바로 이동한다. 도착한 장의 요소는 추가 입력 없이 자동으로 순차 재생한다. 애니메이션을 끝내거나 요소를 하나씩 공개하기 위해 탐색 입력을 소비하지 않는다. 모든 입력 경로가 동일한 상태 전이 함수를 사용하며 이벤트 중복 처리로 두 장 이동하지 않게 한다. 사용자가 별도로 요청한 경우에만 수동 단계 노출을 사용하고, 그 경우에도 클릭 단계를 과도하게 쪼개지 않는다.
- **부드럽고 짧은 자동 재생:** 제목 → 핵심 내용 → 보조 시각물처럼 의미 단위로 묶어 등장시킨다. 줄·단어마다 긴 애니메이션을 붙이지 않는다. 기본 권장값은 요소당 200~400ms, 그룹 간 80~150ms 간격이며 전체 등장 흐름은 대략 1초 안팎으로 마친다. 자동 재생은 장 내부의 등장 효과만 뜻하며 다음 슬라이드로 자동 이동하지 않는다. 장을 떠나면 해당 장의 타이머·애니메이션을 취소해 이전 재생이 새 장에 영향을 주지 않게 한다. 뒤로 돌아온 장은 내용을 즉시 보여주어 재생을 다시 기다리지 않게 하고, `prefers-reduced-motion`에서는 등장 효과 없이 전체 내용을 표시한다.
- **빠른 입력은 빠르게 반응:** 빠른 연타와 키를 누르고 있는 동안의 반복 입력을 누락하지 않는다. 애니메이션 완료 대기, 고정 cooldown, 긴 debounce로 탐색을 잠그지 않는다. 상태는 입력 즉시 갱신하고 진행 중 전환은 취소하거나 최신 상태로 마무리하여 입력을 멈춘 뒤 뒤늦게 넘어가지 않게 한다. 휠은 마우스와 트랙패드의 delta 단위를 정규화하고 작은 이벤트를 누적해 과민 반응을 막되, 빠른 스크롤과 방향 반전은 즉시 반영한다. **휠 이동량은 항상 한 장으로 제한한다.** delta의 크기·속도·단위가 커도 이동 장수로 환산하지 않는다. 임계값에 도달하면 방향에 따라 정확히 한 장만 이동하고 누적량을 초기화한다. 남은 delta를 다음 장 이동으로 이월하거나 한 이벤트에서 여러 번 이동하지 않는다. 빠르게 연속해서 돌릴 때도 각 이동 처리는 한 장씩만 수행한다.
- **전체화면:** 마우스 우클릭 또는 `F`/`f`로 브라우저 전체화면 진입·해제를 전환하고 `Esc` 해제도 처리한다. 덱의 `contextmenu` 이벤트에서 기본 컨텍스트 메뉴를 막고, 키보드와 동일한 전환 함수를 호출한다. `document.fullscreenElement`를 기준으로 `requestFullscreen()` 또는 `exitFullscreen()`을 호출하며 우클릭이 슬라이드 이동이나 다른 클릭 동작을 일으키지 않게 한다. 전체화면 변경과 창 크기 변경 시 무대 배율을 다시 계산한다. 전체화면 요청이 거부되거나 지원되지 않아도 현재 장과 조작은 유지하고, 처리되지 않은 오류를 남기지 않는다.
- **최소 UI:** 이전·다음 버튼을 포함한 슬라이드 조작 버튼을 화면에 만들지 않는다. 발표자 메모, 발표자 모드, 메모 패널, 도움말·목차·설정·전체화면 버튼이나 오버레이도 만들지 않는다. 키·휠 사용법을 설명하는 문구, 단축키 범례, 조작 안내용 툴팁·도움말은 덱과 전달 메시지에 따로 넣지 않는다. 어려운 용어·개념을 설명하는 콘텐츠 툴팁은 허용하고 필요한 곳에 적극 활용한다. 하단 진행 표시는 유지하고 접근성용 현재 위치 정보를 제공한다. 콘텐츠 이해를 위한 상세 정보 펼치기·접기와 라이브 위젯은 이 제한과 별개다. 필요한 경우 별도 요청 없이 적용할 수 있다.
- **하단 진행 표시 필수:** 현재 슬라이드가 전체 흐름의 어디쯤인지 하단에서 알 수 있게 한다. 현재/전체 장수, 진행선, 구간 표시 등 표현은 덱의 디자인에 맞게 창의적으로 정하되 위치와 진행 정도가 명확해야 한다. 클릭을 유도하는 추가 탐색 버튼이 아닌 간결한 상태 표시로 만들고 본문을 가리지 않는다. 모든 이동 경로와 해시 직접 진입에서 현재 장 상태에 맞춰 즉시 갱신하며, 전체화면과 다른 화면 비율에서도 보이게 한다. 접근성용으로 현재 장과 전체 장수를 제공한다.
- **입력 충돌 방지:** 입력 필드·편집 영역·슬라이더 등 라이브 위젯의 키 입력을 가로채지 않는다. 링크·버튼에 포커스가 있으면 `Enter`·`Space`의 원래 동작을 보존하고, 브라우저·운영체제의 `Ctrl`/`Alt`/`Meta` 조합 단축키도 가로채지 않는다. 내부 스크롤 영역과 브라우저 확대용 수정키+휠을 보존하고, 덱 탐색으로 처리한 이벤트만 기본 동작을 막는다.
- **화면 비율이 달라도 경계가 보이지 않게:** 콘텐츠는 1920×1080 비율을 유지해 화면 안에 온전히 맞춘다. 무대 바깥 여백과 현재 슬라이드는 같은 배경으로 이어지게 하고, 무대 외곽 테두리·그림자·둥근 모서리·대비되는 레터박스를 넣지 않는다. 그라데이션·이미지 배경은 뷰포트 전체의 공통 배경 레이어로 확장해 경계에서 끊기지 않게 한다. 장마다 배경이 바뀌면 바깥 배경도 함께 갱신한다. 경계를 숨기려고 콘텐츠를 늘이거나 잘라내지 않는다.

## 작업 순서

### 1. 브리프를 좁힌다

무엇을 만들지 정해지지 않았으면 먼저 정한다. 발표는 세 가지가 정해지면 구조가 따라온다.

- **시간과 형식.** 5분 피치인지 15분 심사인지, 라이브 데모가 끼는지.

  분량은 **슬라이드별 설명 시간과 전체 발표 시간**으로 잡는다. 기본은 한 번의 입력으로 한 장 이동이며, 장 안의 자동 등장 요소 수를 클릭 수로 계산하지 않는다. 애니메이션을 기다리는 시간이 설명 흐름을 끊지 않도록 짧게 유지한다. 라이브 데모 시간은 별도로 확보하고, 내용이 많으면 수동 클릭 단계를 늘리는 대신 장을 나눈다.

- **청중과 그들이 던질 질문.** 심사위원인지 경영진인지 동료인지. 그들이 "그게 진짜냐"를 물을 자리가 어디인지.
- **덱이 이기려는 한 문장.** 청중이 하나만 기억한다면 무엇인가.

### 2. 소재를 실물에서 확인한다

발표 자료를 문서만 보고 만들면 "우리는 ~합니다"만 늘어놓게 된다. 청중이 듣고 싶은 것은 그게 진짜냐는 증거다.

프로젝트 안에서 만드는 덱이면 **코드와 데이터를 직접 열어 확인한다.** 문서가 주장하는 기능이 실제로 있는지, 규모 숫자를 저장소에서 셀 수 있는지, 실제 값이 무엇인지. 대개 문서가 자기 제품을 과소평가하고 있고, 실측값이 문서의 형용사보다 강하다.

확인한 실측값은 그대로 쓴다. 없는 숫자를 만들지 않는다.

### 3. 서사를 정한다 — 기능 나열이 아니라 한 건 관통

기능을 6개 나열하면 청중 머리에 하나도 안 남는다. **실제 사례 하나를 끝까지 따라가는 구조**가 거의 항상 이긴다.

기본 골격:

```
문제        왜 지금 이게 문제인가 (짧고 세게)
접근        어떤 관점으로 푸는가
관통 사례   실제 한 건을 처음부터 끝까지     ← 덱의 심장, 분량의 1/3
신뢰        못 믿는 사람을 위한 근거·반증
규모        그래서 얼마나 쌓였는가
한계        하지 않는 것 (정직하게)
```

관통 사례를 고를 때는 **데이터가 가장 두껍게 쌓인 것**을 고른다. 가장 인상적인 사례가 아니라, 끝까지 파고들었을 때 빈 곳이 없는 사례다.

"규모"를 "신뢰" 뒤에 두는 것에 이유가 있다. 숫자를 먼저 던지면 "그래서 정확해?"가 남고, 근거를 먼저 보이면 숫자가 신뢰의 결과로 읽힌다.

### 4. 미감을 정한다

**여기서 `frontend-design` 스킬을 읽는다.** 팔레트·타이포·서명 요소를 브리프에 맞게 정하는 판단은 그 스킬이 다룬다. 이 스킬은 그 위에 얹는 덱 역학만 담당한다.

덱에만 해당하는 것 둘:

- **서명 요소는 소재에서 나와야 한다.** 장식이 아니라 그 주제가 참인 무언가를 인코딩할 때만 기억에 남는다. (예: 사실과 가정을 구분하는 것이 논지인 제품이라면, 덱의 모든 숫자에도 `확인값`/`가정` 표시를 붙인다. 자기 주장을 자기 자료가 지키는 셈이다.)
- **동적인 움직임을 적극 활용한다.** 부드러운 순차 등장뿐 아니라 흐름을 따라 움직이는 선·입자, 변화하는 도표, 상태 전환, 시뮬레이션, 입력에 반응하는 움직임 등 생동감 있는 표현을 선호한다. 모션 개수를 일률적으로 제한하지 않고 주제·시선 흐름·설명에 맞춰 설계한다. 본문은 읽는 동안 안정적으로 유지하고, 지속·반복 모션은 흐름이나 변화를 보여주는 시각 요소에 사용한다. 움직임 때문에 추가 클릭이나 대기가 필요해지지 않게 하며, 빠른 장 이동은 즉시 반영한다. 비활성 슬라이드의 반복 애니메이션은 중단하고 `prefers-reduced-motion`에서는 정적인 대체 상태를 제공한다. 구현 참고는 `references/reveal.md`.

브랜드색이 하나 주어졌으면 그 한 색에서 팔레트를 파생시킨다 → `references/palette.md`

**이미지 생성이 가능한 환경에서는 적극 활용한다.** 사용자 환경상 집에서는 가능하고 회사에서는 사용할 수 없으므로, 현재 환경과 제공된 도구·사용자 제약을 확인해 결정한다. 가능하면 개념 일러스트·오브젝트·캐릭터·설명용 시각 자료 등 생성 이미지가 이해도와 완성도를 높이는 곳에 활용한다. 이미지 생성 작업에는 사용 가능한 이미지 생성 스킬·도구를 적용한다. 회사처럼 사용할 수 없는 환경에서는 외부 생성 서비스로 우회하지 않고 HTML/CSS·SVG·도표·사용자 제공 이미지 등으로 구성한다. 생성 기능이 없어도 덱 제작을 진행하며 생성했다고 보고하지 않는다.

**생성 이미지는 실제 투명 배경을 기본으로 한다.** 슬라이드 위에 자연스럽게 배치할 수 있도록 알파 채널이 있는 PNG 또는 WebP로 만들고, 흰색·검은색 사각 배경이나 투명도를 흉내 낸 체크무늬를 이미지에 넣지 않는다. 프롬프트 단계부터 슬라이드의 팔레트·표현 스타일·조명·시점·배치 공간에 맞춰 요청한다. 과도한 외곽 여백, 잘린 피사체, 흰 테두리·배경색 잔여물 없이 자연스러운 가장자리를 확보한다. 그림자도 슬라이드 배경과 어울리게 처리하고, 투명 이미지 주위에 불필요한 카드나 프레임을 덧씌우지 않는다. 읽어야 하는 텍스트와 정확한 수치·관계는 HTML·SVG로 작성해 선명도와 수정 가능성을 유지한다.

생성 후 파일의 실제 투명도와 가장자리 품질을 확인하고, 최종 슬라이드 배경 위에 합성된 상태에서 색감·크기·구도·여백·본문과의 조화를 검증한다. 단일 HTML 산출물에는 이미지를 내장해 로컬 파일 경로나 외부 이미지 주소에 의존하지 않게 한다. 투명 출력을 지원하지 않거나 결과가 불투명하면 투명하다고 간주하지 말고, 허용된 이미지 편집 도구로 보정하거나 SVG 등 자연스럽게 통합되는 대안으로 바꾼다.

**장면별로 다양한 시각 자산을 계획한다.** 먼저 각 장의 메시지·설명 장면·이미지 역할을 정하고, 이에 필요한 대상·행동·표정·포즈·시점·소품·상태를 같은 화풍과 팔레트의 자산 세트로 준비한다. 소수의 이미지를 덱 전체에 돌려 쓰지 말고 새 개념이나 상황에는 그 내용을 설명하는 자산을 생성·확보한다. 색·크기·좌우 반전·위치만 바꾼 같은 그림은 새로운 장면으로 보지 않는다. 일관성은 화풍과 인물 정체성으로 유지하며, 같은 개체의 변화 추적이나 의도적인 회상을 보여줄 때만 동일 자산을 재등장시킨다. 로고·범례 등 고정 식별 요소는 유지할 수 있지만 장면 다양성을 대신하지 않는다. 픽셀 아트·종이 콜라주·입체 일러스트 등 스타일은 주제와 슬라이드 테마에 맞춰 선택하며, 참고 이미지의 특정 화풍을 모든 덱의 기본값으로 삼지 않는다. 필요한 장면이 부족하면 자산 세트를 보강하되 쓰지 않을 자산을 대량 생성하지 않는다.

스타일을 한눈에 확인하는 재료 시트와 실제 배치용 개별 자산을 구분한다. 시트로 생성할 때는 요소가 겹치거나 잘리지 않도록 충분한 간격을 두고, 격자 크기는 자산 수에 맞게 정한다. 6×6 같은 규격을 강제하지 않는다. 실제 사용 시에는 개별 투명 이미지로 분리하거나 독립적으로 표시할 수 있는 스프라이트 좌표를 정의한다. 분리·보정 작업은 사용 가능한 이미지 편집 스킬과 도구 지침을 따르고, 체크무늬가 박힌 스크린샷을 투명 원본으로 취급하지 않는다. 필요한 자산만 수정·재생성해 세트 전체의 스타일을 유지한다. 생성 불가 환경에서는 직접 작성한 SVG나 사용 가능한 제공 자산으로 같은 제작 방식을 적용한다.

**이미지를 설명 장면의 일부로 창의적으로 사용한다.** 옆에 붙인 장식이나 공중에 둥둥 떠다니는 오브젝트를 기본 패턴으로 삼지 않는다. 캐릭터가 재료를 조립·분류·검토하는 장면, 사물이 공정을 통과하며 바뀌는 과정, 분해도와 단면으로 내부를 드러내는 구성, 전후 상태의 교체, 확대 관찰과 주석, 도표·타이포와 결합한 시각적 비유 등 내용의 관계에 맞는 연출을 선택한다. 이 예시들을 순서대로 반복하는 템플릿으로 쓰지 말고 새로운 주제에서도 이미지가 무엇을 설명하는지 먼저 판단한다. 정적인 구도가 가장 명확하면 그대로 사용한다.

필요한 요소를 별도 HTML/SVG 레이어로 배치해 등장·결합·분리·이동·상태 변화를 제어한다. 움직임에는 시작 상태, 변화 이유, 도착 상태가 있어야 하며 설명 순서·인과·비교·관계를 드러내야 한다. 의미 없는 상하 부유·회전·맥동 루프를 모든 이미지에 일괄 적용하지 않는다. 지속 모션은 실제 흐름이나 반복 과정을 설명할 때 사용한다. 장면은 한 번의 장 이동 뒤 자동으로 이어지며, 텍스트를 읽는 영역은 안정적으로 유지하고 이미지가 본문·툴팁·진행 표시를 가리지 않게 한다. 생성이 불가능하거나 자산이 부족하면 내용에 맞는 SVG·도식·제공 이미지로 장면을 구성하며 같은 그림의 반복으로 빈자리를 채우지 않는다.

자산별 식별자·용도·기준 크기·기준점과 필요한 경우 스프라이트 좌표를 관리한다. 확대에 적합한 해상도를 확보하고, 픽셀 아트는 의도한 픽셀 질감을 보존한다. 분리 후에는 이웃 자산 혼입·가장자리 잘림·불필요한 투명 여백을 확인한다. 최종 장면에서는 최소/최대 배율, 이동 경로의 겹침·잘림, 빠른 장 이동 시 잔여 애니메이션, 반복 재생 성능, 감소된 모션 설정을 검증한다. 주제별 자산 원본·시트·개별 파일은 해당 프로젝트의 `output/` 아래에서 관리하고 최종 단일 HTML에는 필요한 자산을 내장한다.



실제 사례를 참고해 디자인·인터랙션을 정할 때는 [HTML 표현 참고 사례](references/html-examples.md)를 읽는다. 기본 방향은 **충분한 설명과 동적인 도식 + 필요한 상세 정보 펼치기 + 장면 사이의 자연스러운 연결**이다.

**HTML의 장점이 보이는 디자인·구성에 가점을 준다.** 정적인 PPT 화면을 그대로 재현하는 데 그치지 않고, HTML에서 자연스럽고 PPT에서는 구현·운영하기 어려운 표현이 주제 이해에 도움이 되는지 우선 검토한다. 예를 들어 조건·입력에 따라 결과가 즉시 바뀌는 계산·시뮬레이션, 같은 자리에서 관점이나 전후 상태를 바꾸는 비교, 필터에 반응하는 도표, 서로 연동되는 데이터·도식, 눌러서 근거까지 탐색하는 구성, 직접 조작하는 프로세스 시연이 적합하다. 예시는 선택지이며 모든 덱에 같은 위젯을 넣거나 기능 수를 채우지 않는다.

**움직임 외에도 정보 구성의 완성도를 높인다.** 아래 원칙을 내용에 맞게 선택하며 모든 장에 같은 레이아웃이나 기능을 강제하지 않는다.

- **본문과 시각 자료의 연동 강조:** 문장·용어·범례에 호버하거나 포커스를 두면 관련 도표 영역도 강조한다. 같은 개념의 이름·색·기호를 일관되게 사용하고, 대응 관계가 분명할 때 양방향 연결을 제공한다. 색만으로 구분하지 않으며 강조가 해제되면 원래 상태로 돌아온다.
- **동일 조건 비교:** 전후·대안은 축·단위·범위·기준 시점·배치를 가능한 한 동일하게 유지해 차이를 바로 읽게 한다. 조건이 다르면 명시하고, 자동 축 변경이나 재배치로 차이를 과장하지 않는다.
- **연결 표현은 하나로 완결:** 같은 연결에 배경 점선·실선과 별도의 화살표 문자를 포개지 않는다. 단독 화살표를 쓰거나 선과 화살촉이 하나로 이어지는 SVG 경로를 사용한다. 점선 화살표가 필요하면 하나의 경로와 끝점 마커로 구성하고, 별도 `→` 문자를 덧씌우지 않는다. 노드 뒤를 관통하는 장식선으로 연결을 흉내 내지 말고 출발·도착 지점과 방향이 명확하게 읽히도록 한다.
- **편집형 레이아웃:** 모든 내용을 똑같은 카드로 쪼개지 않는다. 소제목·문단·비교표·인용·도식의 역할에 맞춰 배치하고 읽는 순서를 만든다. 충분한 본문 설명을 유지하면서 관련 도표와 근거를 가까이 둔다.
- **전체에서 사례로 탐색:** 전체 경향과 핵심 해석을 기본 화면에 제시한 뒤, 필요하면 필터·검색·항목 선택으로 구체적 사례를 확인하게 한다. 현재 조건과 결과 범위를 명확히 하고 일부 사례를 전체의 결론처럼 제시하지 않는다.
- **근거까지 연결:** 핵심 수치·주장에는 정의·단위·기간·출처·해석상 한계를 연결한다. 용어와 수치의 뜻은 호버만으로 읽게 하고, 원문·가공 방법·여러 근거 비교는 필요할 때 상세 펼치기나 출처 링크로 제공한다. 근거가 없으면 만들지 않고 불확실성을 표시한다.
- **사례와 원리를 연결:** 구체적 사례가 어떤 원리를 보여주는지 설명하고, 필요하면 조건을 바꿔 성립 범위와 예외를 비교하게 한다. 조작하지 않아도 대표 사례와 핵심 결론을 이해할 수 있어야 한다.

인터랙션은 장식이나 기술 과시보다 설명력을 높여야 한다. 정적 표현으로는 전달하기 어려운 변화·관계·차이를 직접 경험하게 하고, 덱의 시각적 완성도와 충분한 본문 설명을 함께 유지한다. 조작하지 않은 초기 상태도 의미 있는 내용을 보여줘야 하며, 관객이 모든 인터랙션을 거치지 않아도 발표 흐름을 따라갈 수 있어야 한다. 콘텐츠용 컨트롤은 허용하되 슬라이드 탐색 버튼·조작 안내를 추가하지 않고, 한 번의 입력으로 장을 넘기는 기본 규칙도 유지한다.

HTML 기능을 사용하면 기본 상태뿐 아니라 입력 변경·초기화·경계값·빈 결과 등 해당 기능의 주요 상태를 확인한다. 인터랙션 뒤에도 탐색·전체화면·하단 진행 표시가 정상이어야 한다. 단일 파일 실행과 오프라인 사용성을 유지하며, 외부 데이터나 서비스가 꼭 필요하면 의존성과 사용할 수 없을 때의 대체 상태를 명확히 한다. PDF 등 정적 버전에는 대표 상태와 핵심 결과를 담아 의미가 빠지지 않게 한다.


### 5. 만든다

`assets/skeleton.html`을 복사해서 시작한다. 무대 스케일링, 내비게이션, 단계 노출, 진행 표시가 들어 있다. 골격의 수동 단계 노출은 기본적으로 장 진입 시 자동 순차 재생으로 바꾼다. 기존 골격의 도움말·이전/다음 버튼을 포함한 조작 버튼은 제거하고 위 기본 조작과 화면 처리 규칙에 맞춘다. 처음부터 짜면 그 함정을 다시 밟는다.

읽을 순서:

| 무엇을 할 때 | 읽을 것 |
|---|---|
| 무대·스케일링·반응형 | `references/stage.md` |
| 단계 노출·SVG 순차 드로잉·카운트업·라이브 위젯 | `references/reveal.md` |

골격은 다크 팔레트가 기본이고, 밝은 경로는 같은 파일 안에 주석 블록으로 들어 있다. 제품 UI와 톤을 맞춰야 하거나 라이브 데모가 밝은 화면이면 그 블록으로 갈아탄다.

**텍스트와 설명이 충분한 슬라이드를 기본으로 한다.** 짧은 구호나 키워드 몇 개만 놓은 내용 빈약한 장을 피한다. 핵심 주장에 설명·이유·구체적 예시·근거·시사점을 함께 담아, 슬라이드만 읽어도 요지가 이해되게 한다. 텍스트가 많다는 이유만으로 무조건 요약하거나 여러 장으로 쪼개지 않는다. 문단·소제목·목록·강조·열 구성을 활용해 정보량과 읽기 쉬운 구조를 함께 확보한다.

**어려운 용어의 부연 설명은 호버로 모두 볼 수 있게 한다.** 대상 청중에게 생소할 용어·약어·추상적인 개념은 해당 표현에 마우스를 올리면 뜻·쉬운 풀이·필요한 예시를 툴팁에서 읽을 수 있게 한다. 용어마다 정의 문단이나 설명 카드를 본문에 늘어놓아 슬라이드 공간을 쓰지 않는다. 본문에는 핵심 주장·논리·중요한 근거를 충분히 담고, 이해를 돕는 용어 해설은 툴팁으로 분리한다. 텍스트가 풍부해야 한다는 원칙을 용어 설명의 반복으로 충족하지 않는다. 설명이 필요한 표현을 빠뜨리지 않되, 청중에게 익숙한 일반 단어까지 기계적으로 툴팁을 붙이지 않는다.

한 개념의 설명은 호버만으로 끝까지 확인할 수 있게 한다. 말줄임·줄 수 제한으로 자르거나 나머지를 보려고 다시 클릭하게 하지 않는다. 길이에 맞춰 툴팁 크기와 배치를 조정하고, 화면 높이를 넘으면 포인터를 옮겨 내부에서 스크롤하며 전체를 읽을 수 있게 한다. 별도의 사례 탐색·시뮬레이션·여러 근거 비교는 기존 클릭형 상세 정보로 제공할 수 있지만, 용어 해설을 읽는 데 추가 클릭을 요구하지 않는다.

브라우저 기본 `title` 툴팁 대신 덱의 색·서체·형태에 맞춘 커스텀 툴팁을 사용한다. **툴팁은 해당 슬라이드 테마에 맞춰 개별 디자인한다.** 브라우저·UI 라이브러리의 기본 디자인이나 모든 덱에 반복 적용하는 범용 프리셋을 그대로 사용하지 않는다. 단순히 기본 툴팁의 색만 바꾸는 수준으로 끝내지 않고, 해당 덱의 시각적 언어에 맞게 표면·형태·타이포·간격·모션을 함께 설계한다. 특정 모서리 반경, 그림자, 말풍선 형태를 고정된 정답으로 삼지 않는다. 밝은 장·어두운 장 등 배경이 달라져도 각 슬라이드와 자연스럽게 어울리고 읽기 쉬워야 한다. 덱의 팔레트·타이포·모서리·표면 질감을 이어받아 완성도 있는 설명 패널로 만든다. 개념명, 쉬운 풀이, 예시가 있으면 크기·굵기·간격으로 위계를 주되 불필요한 제목이나 빈 구역은 만들지 않는다. 폭과 줄 길이는 읽기 편하게 조절하고 문단을 정돈한다. 배경과 구분되는 섬세한 테두리·그림자, 필요한 경우 포인터 방향 표시, 짧고 부드러운 등장·퇴장 효과를 활용한다. 장식은 설명을 가리지 않고, 호버 대상과 툴팁의 시각적 연결이 명확해야 한다. 짧은 정의와 긴 설명 모두 디자인이 자연스럽게 대응하도록 한다. 미세한 밑줄이나 강조로 대상임을 자연스럽게 알리고, 충분한 대비와 읽을 수 있는 글자 크기, 정돈된 내부 간격, 절제된 그림자와 짧은 등장 효과로 완성한다. 화면 가장자리에서는 위치를 뒤집거나 보정해 잘리지 않게 하고, 무대의 배율·전체화면에서도 대상과 위치가 맞아야 한다. 포인터를 툴팁 위로 옮겨도 읽을 동안 유지하고, `Esc`나 대상 이탈로 닫을 수 있게 한다. 키보드 포커스로도 같은 정보를 제공하고 `aria-describedby` 등으로 연결한다. 터치에서는 탭으로 열고 닫는 대안을 제공하며, 툴팁 조작이 슬라이드를 넘기지 않게 한다. 장 이동 시 열린 툴팁은 닫는다.

**필요하면 눌러서 추가 정보를 본다.** 용어·문장·카드·도표의 항목을 누르면 상세 설명, 구체적 예시, 비교, 출처·근거 등을 펼쳐 볼 수 있는 구성을 선호한다. 모든 요소에 일률적으로 적용하지 말고, 본문 흐름을 유지하면서 깊이를 더할 때 사용한다. 핵심 설명은 기본 화면에 충분히 남겨 두고, 내용을 빈약하게 만든 뒤 대부분을 클릭 뒤에 숨기지 않는다. 기본은 인라인 펼치기·접기이며 공간상 필요하면 상세 패널을 사용한다. 조작 안내 문구를 덧붙이지 않고도 상호작용 가능한 항목과 펼침 상태가 디자인으로 구분되게 한다.

상세 정보 조작은 슬라이드를 넘기지 않으며, 추가 정보를 모두 열어야 다음 장으로 갈 수 있는 구조를 만들지 않는다. 클릭 이벤트 전파로 장이 이동하지 않게 하고, 키보드 포커스와 `Enter`/`Space` 조작, 펼침 상태의 접근성 정보를 제공한다. 펼친 뒤에도 내용·하단 진행 표시가 잘리거나 겹치지 않게 한다. PDF 등 정적 산출물에서는 클릭 없이도 추가 정보를 읽을 수 있도록 펼친 상태나 별도 보충 페이지로 제공한다.

**한 장에 하나의 중심 주제.** 이는 한 문장이나 한 가지 정보만 넣으라는 뜻이 아니다. 같은 주제를 뒷받침하는 여러 설명과 비교를 충분히 담는다. 중복 표현과 과한 간격을 먼저 정리하고 배치를 조정한 뒤에도 읽을 수 있는 글자 크기에서 내용이 넘치거나 서로 다른 주제가 섞이면 장을 나눈다. 내용을 채우려고 글자를 지나치게 작게 만들거나 근거 없는 내용을 추가하지 않는다.

**불필요한 여백은 내용으로 채운다.** 제목만 작게 놓거나 작은 카드 몇 개만 배치해 화면 대부분을 비워 두지 않는다. 넓게 빈 영역이 있으면 해당 장의 핵심을 이해하는 데 필요한 설명·구체적 예시·비교·근거·도식·이미지를 보강하고, 콘텐츠 크기와 배치를 조정해 무대를 충분히 활용한다. 한 장의 주제는 유지하며, 공간을 채우려고 무관한 내용·중복 문구·장식이나 확인되지 않은 사실을 추가하지 않는다. 제목과 본문 사이, 카드 내부, 열 사이의 과한 간격은 줄이되 가독성에 필요한 여백과 안전 여백은 남긴다. 화면 비율 차이로 생긴 무대 바깥 영역은 앞의 공통 배경 규칙으로 처리하고, 내용을 잘라내거나 왜곡해 채우지 않는다.


### 6. 검증한다 — 눈으로 보는 것으로 끝내지 않는다

여기가 이 스킬의 핵심이다. 덱의 결함은 대부분 **발표 당일에** 드러난다. 미리 잡을 수 있는 것들을 스크립트로 잡는다.

```bash
# 브라우저에서 페이지를 열고, 아래 스크립트를 페이지 컨텍스트에서 실행한다
# (Claude Browser javascript_tool / playwright browser_evaluate / devtools 콘솔 무엇이든)
cat scripts/audit.js
```

이 감사가 잡는 것 — 무대가 눌렸는지(`flex-shrink`), `scale(0)`으로 화면이 사라졌는지,
전 슬라이드 넘침(세 방식으로 교차 확인), flex 축소로 내용이 박스를 흘러넘쳤는지,
모노 서체에 갇힌 한글, 한글에 걸린 `uppercase`·과한 음수 자간, `keep-all` 누락,
단계 번호 불연속, 하드코딩된 장 번호, `hashchange` 누락, 컨트롤 장에 `data-noclick` 누락,
어두운 배경에 얹힌 QR.

**그라데이션 배경을 썼으면 대비는 픽셀로 재야 한다.** 계산된 `background-color`로는 절대 검사되지 않는다.

```bash
python scripts/contrast.py bgonly.png "#EBF2F8" "#B8C7D4" "#8CD2F5"
```

절차와 함정(1~2px 입자를 배경으로 오독하는 문제)은 `references/verify.md`.

추가로 브라우저에서 아래 동작을 검증한다. 정적 감사만으로 입력 반응성이나 화면 경계가 검증됐다고 보고하지 않는다.

- 애니메이션이 있는 장과 없는 장 모두 한 번의 입력으로 한 장 이동하는지 확인한다. 진입한 장은 추가 클릭 없이 순차 등장하고, 재생 도중 다음을 눌러도 즉시 다음 장으로 이동해야 한다. 뒤로 이동, 첫/마지막 장의 범위 제한, `Home`/`End`, 감소된 모션 설정도 확인한다.
- 개념 툴팁은 호버·키보드 포커스·터치 대안으로 같은 정보를 볼 수 있는지 확인한다. 툴팁으로 포인터 이동 시 유지, `Esc` 닫기, 장 이동 시 정리, 화면 가장자리·무대 배율·전체화면에서의 위치와 잘림, 탐색 입력과의 충돌을 확인한다. 긴 설명도 말줄임이나 추가 클릭 없이 끝까지 읽을 수 있고, 툴팁 내부 스크롤이 장 이동을 일으키지 않는지 확인한다. 실제 열린 툴팁을 화면에서 확인해 덱과의 디자인 일관성, 설명 위계, 글자 크기·대비·줄바꿈·내부 여백, 등장·퇴장 효과를 검증한다. 짧은 설명과 긴 설명을 각각 확인한다.
- 연동 강조는 올바른 대상에 연결되고 해제·장 이동 시 정리되는지 확인한다. 비교의 축·단위·조건, 필터의 기본·선택·빈 결과 상태, 표시 수치와 출처의 일치도 해당 기능이 있을 때 확인한다.
- 추가 정보가 있는 경우 마우스·키보드로 열기와 닫기를 확인한다. 상세 조작이 장 이동을 일으키지 않고, 상세 정보를 열지 않아도 다음 장으로 이동할 수 있어야 한다. 펼친 상태의 넘침·겹침과 정적 산출물의 추가 정보 포함 여부도 확인한다.
- 빠른 연타·키 반복·빠른 휠·트랙패드·즉시 방향 반전을 확인한다. 휠은 작은 delta 누적, 큰 delta, pixel/line/page 단위, 양방향, 빠른 연속 이벤트에서도 한 번의 이동 처리가 한 장을 넘지 않는지 검증한다. 입력 누락, 중복 이동, 입력 종료 후 지연 이동이 없어야 한다.
- 우클릭 진입·다시 우클릭 해제, `F` 진입·재입력 해제, 우클릭과 `F`를 번갈아 사용한 전환, `Esc` 해제와 전체화면 불가 시 상태 유지를 확인한다. 우클릭 시 기본 컨텍스트 메뉴가 나타나지 않고 현재 장이 이동하지 않는지도 확인한다. 입력 필드와 내부 스크롤 영역의 조작도 확인한다.
- 16:9, 16:10, 4:3, 초광폭, 세로형 뷰포트에서 콘텐츠 잘림·왜곡과 무대 외곽 경계가 없는지 확인한다. 밝은/어두운 배경 및 배경이 달라지는 장 전환도 확인한다.
- 각 장을 실제 화면으로 확인해 키워드·구호만 있고 설명이 부족한 장이나 불필요하게 큰 빈 영역이 없는지 살핀다. 슬라이드 자체에 핵심을 이해할 설명·예시·근거가 충분한지 확인한다. 빈 영역은 관련 내용·예시·시각 자료 보강과 배치 조정으로 해소하고, 보강 후에도 한 장의 주제·글자 가독성·넘침 방지가 유지되는지 확인한다.
- 덱 전체의 썸네일과 자산별 사용 장 목록을 함께 확인해 동일 이미지·유사 포즈·같은 배치의 관성적인 반복을 찾는다. 재등장에 설명상 이유가 없으면 장면에 맞는 다른 자산이나 구도로 교체한다. 연속 장뿐 아니라 떨어진 장의 반복도 확인하고, 대표 모션은 실제 재생해 단순 부유 효과만 바뀌는 구성이 아닌지 살핀다. 신규 개념, 동일 개체의 상태 변화, 생성 불가 시 대체 장면에도 이 기준을 적용한다. 감소된 모션과 PDF의 정적 상태에서도 이미지의 설명 역할이 남아야 한다.
- 흐름도·관계도·타임라인의 각 연결을 확인한다. 점선과 화살표 문자, 중복 경로, 가상 요소의 장식선이 포개져 이중 선이나 어긋난 화살촉으로 보이지 않아야 한다. 공통 연결 스타일을 바꾸면 이를 쓰는 모든 장을 확인하고, 새 노드 수·긴 라벨·무대 축소·애니메이션 중간 상태·정적 출력에서도 연결 방향이 선명한지 검증한다.
- 이전·다음 버튼을 포함한 슬라이드 조작 버튼과 발표자 메모·조작 설명·단축키 안내가 없는지 확인한다. 모든 필수 이동 키와 위젯 포커스·수정키 조합의 충돌 방지를 확인한다. 하단 진행 표시가 첫 장·중간 장·마지막 장·해시 직접 진입에서 정확히 갱신되고, 전체화면과 다른 화면 비율에서도 본문을 가리지 않는지 확인한다. 실행하지 못한 항목은 미검증으로 보고한다.

발표 자료는 되돌릴 기회가 없다. 검증 없이 "다 됐습니다"라고 말하지 않는다.

### 7. 넘긴다

- 최종 파일 위치와 검증 결과를 전달한다. 사용자가 별도로 묻지 않으면 `F`나 슬라이드 이동 방법 등 조작 설명은 덱에도 전달 메시지에도 넣지 않는다.
- 백업 PDF를 만들어 둔다: `python scripts/export_pdf.py deck.html` — 행사장 브라우저가 말을 안 들을 때를 위한 보험이다.
- 폰트를 CDN에서 받는 구성이면, 오프라인 위험을 알리고 폴백이 무엇인지 말해준다.

## 자주 하는 실수

**시간을 안 정하고 만들기.** 분량이 정해지지 않으면 다 넣게 되고, 다 넣으면 발표가 안 끝난다.

**정보량을 무조건 줄이기.** 텍스트나 표가 많다는 이유만으로 키워드 몇 개로 축약하지 않는다. 설명에 필요한 비교표와 문장은 유지하고, 행·열의 위계와 강조로 읽는 순서를 만든다. 표의 행 수를 일률적으로 제한하지 말고 실제 화면에서 글자 크기와 가독성을 확인한다.

**제품 UI 규칙을 덱에 그대로 적용하기.** 제품이 모션·그라데이션을 금지해도 덱은 다른 매체다. 반대로 덱의 화려함을 제품에 들고 가지도 않는다. 라이브 데모로 넘어가는 구성이면 톤 차이가 청중에게 보이므로, 그 전환을 의도적으로 설계한다.

**한계를 숨기기.** 심사위원은 약점을 찾는다. 먼저 말하면 신뢰가 되고, 숨기면 찔린다. 데이터가 한쪽에 몰려 있으면 그 비대칭의 이유를 먼저 설명한다.
